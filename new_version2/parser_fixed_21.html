1) Область и точность

Это «полный список грамматик и возможностей» для версии prompt_parser_fixed_v21: включая Lark-правила, regex-правила, шаговые расписания, attention-парсинг, AND/мультикондишн, строгую валидацию, а также новые conditioning/backend-слои CHUNK, BLEND и MORPH.

В этом документе «грамматика» понимается в двух слоях: формальная Lark-грамматика + регулярные синтаксические шаблоны, которые код обрабатывает до/после Lark.

2) Архитектура парсинга

1) Нормализация входа
AND, пробелы, scheduler-surface
2) Fast-path
postfix/inner/ranges regex
3) Lark parse
_grammar -> parse tree
4) CollectSteps
семантика правил в schedule
5) Финализация
collapse/unescape/AND cleanup

Ключевые этапы:

  1. _normalize_and_operators_for_parse: приводит AND к внутреннему & и защищает \&.
  2. _normalize_scheduler_surface_syntax: канонизирует записи вроде ] : 10 в ]:10.
  3. _placeholderize_attention_interpolations (v21): pre-pass для форм (body:w0->w1), включая вложенные () и optional easing ~mode.
  4. _placeholderize_postfix_scheduled_blocks: временно заменяет запятые в [...]:N внутри блока (чтобы Lark не ломался).
  5. _try_fast_after_scheduler: быстрый путь для [...]:N и [...]:N a-b,c-d.
  6. Если fast-path не применим: Lark-парсинг + CollectSteps.
  7. _expand_attention_interpolations (v21): post-pass разворачивает маркеры интерполяции на каждом шаге активного интервала.
  8. _finalize_schedules: _apply_and + _collapse_spaces, возврат [[end_step, text], ...].

3) Полная Lark-грамматика (как в коде)

alternate — динамическое правило: при ALLOW_EMPTY_ALTERNATE=1 разрешаются пустые варианты между |.

Важно: правило compound объявлено в grammar-блоке, но напрямую не включено в prompt; на практике underscore-токены обычно проходят через plain. 

!start: (prompt | /[():,!|&]/+)*

prompt: (scheduled | emphasized | grouped
        | alternate | alternate_distinct
        | alternate1 | alternate2
        | top_level_sequence3 | top_level_sequence | sequence
        | weighted | numbered | and_rule
        | plain | WHITESPACE)*

!emphasized: "(" prompt ")"
           | "(" prompt ":" prompt ")"
           | "(" prompt ":" NUMBER ")"

!weighted: plain ":" NUMBER

scheduled: "[" [prompt (":" prompt)* ":" NUMBER (WHITESPACE* step_range_list)?] "]" (WHITESPACE* reverse_flag)?
        | "[" [prompt (":" prompt)*] "]" ":" NUMBER (WHITESPACE* step_range_list)? (WHITESPACE* reverse_flag)?
reverse_flag: "reverse"
step_range_list: step_range (WHITESPACE* "," WHITESPACE* step_range)*
step_range: NUMBER "-" NUMBER        -> range_abs
          | NUMBER "%" "-" NUMBER "%" -> range_pct

alternate: "[" prompt ("|" [prompt])+ "]"            // if ALLOW_EMPTY_ALTERNATE=1
alternate: "[" prompt ("|" prompt)* "]"              // if ALLOW_EMPTY_ALTERNATE=0

!alternate_distinct: "[" prompt ("|" prompt)* "]!"
alternate1: (prompt) "|" (prompt)+
alternate2: plain ("|" plain)+

grouped: "{" ((NUMBER_Q | prompt | sequence | grouped) ("," | "|")?)+ "}"

top_level_sequence: prompt ("::" sequence)+ "!!" ("," plain)?
top_level_sequence3: prompt ":::" (sequence | plain) (WHITESPACE* "," WHITESPACE* (sequence | plain))* "!!!" (WHITESPACE* "," WHITESPACE* (plain | sequence))*
sequence: prompt "::" prompt ("," | WHITESPACE)* nested_sequence* ("!" | ";")?
nested_sequence: "::" prompt ("," | WHITESPACE)* ("!" | ";" | "~")?

compound: /[a-zA-Z0-9]+(_[a-zA-Z0-9]+)+/
numbered: NUMBER_Q ("!" | "_")? (grouped | sequence | alternate | alternate_distinct | alternate2 | alternate1)

and_rule: (plain | weighted | emphasized | numbered | grouped | alternate | alternate_distinct | alternate2 | alternate1 | scheduled) ("&" (plain | weighted | emphasized | numbered | grouped | alternate | alternate_distinct | alternate1 | scheduled))+
WHITESPACE: /\s+/
plain: /([^\\[\]\{\}\(\),&:!|]|\\.)+/

%import common.SIGNED_NUMBER -> NUMBER
%import common.INT -> NUMBER_Q

Внутренний _ColonState отслеживает двоеточие вне скобок: ждёт число после :; если число не пришло, двоеточие возвращается в текст. Это предотвращает ложное взвешивание при обычных текстовых двоеточиях.

7) Правила расписаний по шагам

7.1 Boundary интерпретация

  • Если форма записана как N% → процент от общего числа шагов.
  • Если 0 < N < 1 → доля от steps (например 0.35 при 20 шагах ≈ 7).
  • Если N >= 1 → абсолютный шаг. Это важно: 1 и 1.0 в v21 больше не трактуются как 100%.
  • После вычисления всегда clamp в диапазон [1..steps].

7.2 Политика ranges

  • Диапазоны применяются в порядке записи.
  • Перекрытие: последний диапазон перезаписывает предыдущий (last-wins).
  • start == end разрешен (один шаг).
  • start > end — ошибка синтаксиса (reverse_range).

7.3 Визуальный образ (timeline)

prompt = [a:b]:10 1-4,6-8, steps=12:

Шаги 1-4
a
Шаг 5
"" (пусто)
Шаги 6-8
b
Шаги 9-12
"" (пусто)

7.4 Префикс/суффикс и пустые сегменты

Для формы с контекстом типа X [a::4] Y пустые внутренние сегменты не удаляются; они превращаются в валидный текст X Y, что важно для SD-практики.

9.2 Стратегия выполнения get_schedule

  1. Валидация входа (_validate_inputs).
  2. Нормализация prompt (AND/scheduler-surface).
  3. Серия fast-path веток (TL3, numbered-alt, inner/postfix/ranges).
  4. При необходимости Lark parse + CollectSteps.
  5. Финализация и (опционально) сворачивание в один сегмент, если use_scheduling=False.

9.3 Seed и детерминизм

  • Если seed=None, используется стабильный sha256-seed от prompt.
  • Кэш возвращает копию (defensive copy), чтобы внешняя мутация не портила кэш.

9.4 Мультикондишн grammar-слой

  • get_multicond_prompt_list в v21 использует top-level split по AND и standalone &, а не тупой split по сырой строке.
  • Split уважает вложенность скобок и escape, поэтому случаи вроде (cat AND dog:1.2) и \(cat AND dog\) не разваливаются на неправильные куски.
  • RE_END_WEIGHT понимает вес в конце подпромпта (text:1.2, включая китайский двоеточие).
  • Это означает, что top-level AND уже поддерживает контролируемые веса веток: например, style:0.7 AND character:1.3 даёт две composable ветки с разным весом, а не attention внутри одной строки.
  • get_multicond_prompt_list строит плоский словарь подпромптов + веса.

10) Прямой помощник-конструктор шаблонов

Ниже спецификация «строгого помощника», который должен знать парсер полностью и помогать пользователю собирать корректные форматы быстрее.

A. Конструктор формы

Выбирает шаблон: plain, emphasized, scheduler, ranges, alternate, sequence, AND, multicond.

B. Валидатор до запуска

Сразу прогоняет lint_prompt, показывает kind/pos/end/token и автопочинку (например 8-4 → 4-8).

C. Предпросмотр шагов

Показывает visualize_schedule и конкретный at_step для выбранных шагов.

D. Режим «без потерь»

Никогда не удаляет экранирование и не заменяет лексемы без согласования, только явные безопасные трансформации.

Минимальный сценарий работы помощника

  1. Определить цель: статический prompt или scheduler.
  2. Предложить 2-3 валидных шаблона для этой цели.
  3. Собрать заполненный prompt с подсветкой грамматики.
  4. Показать расписание, ошибки, и безопасные правки.
  5. Выдать итог + «почему так» (семантика шагов и весов).

Builder теперь синхронизирован с v21 не только по старой grammar-части, но и по новым backend-слоям. Он остаётся frontend-конструктором: финальную tensor-математику делают Python/backend-слои, а UI собирает корректный синтаксис для поддерживаемых builder-блоков и даёт безопасный preview. В builder появился и отдельный pooled-only adjunct POOL{...}: он сериализуется как top-level side prompt, не считается отдельным backend-блоком и может сосуществовать с plain text или одним backend в той же AND-ветке. Там же теперь есть и ASSEMBLE{enc1=...; enc2=...; pooled=...}: это top-level SDXL-style post-assemble backend, который собирает уже готовые enc1 / enc2 / pooled каналы из отдельно закодированных prompt-ов и не притворяется настоящим dual-encoder pre-encode routing. В builder теперь есть и отдельный блок BIND{owner => attrs}: это owner-binding adjunct, который создаёт скрытые composable ветки и сильнее привязывает признаки к owner, чем plain text. В том числе builder знает safe sugar-формы CHUNK + tail MORPH и MORPH + tail CHUNK в одной AND-ветке, если там ровно по одному такому backend-блоку и нет BLEND. Важно: его lint остаётся эвристическим и не заменяет строгий Python lint_prompt() для всех raw-text edge cases. Builder-preview при top-level AND вокруг backend-блоков теперь тоже раскладывается по отдельным веткам prompt и заметно ближе к Python multicond preview, но всё равно остаётся эвристическим UI-слоем, а не заменой runtime.

12) Чеклист «абсолютно точного знания парсера»

Помощник считается «полным», только если умеет объяснить и корректно применить:

  • все Lark-правила из раздела 3, включая динамику ALLOW_EMPTY_ALTERNATE;

  • AND-нормализацию и экранирование \&;
  • sequence DSL: ::, !!, !!!, терминации ! ; ~;
  • группы {...} и ограничения комбинаторного взрыва;

Итог: да, парсер поддерживает очень широкий DSL-слой. Но для стабильной UX-работы обязательно использовать помощник через «сборка шаблона → lint → schedule preview → финал».

13.2 Easing-кривые

linear      : t
ease-in     : t^2
ease-out    : t * (2 - t)
ease-in-out : t^2 * (3 - 2t)

13.3 Backward compatibility и стабильность

  • Старый формат без ~mode работает как раньше (linear по умолчанию).
  • Unknown mode (например ~banana, ~ease_in) не ломает парсинг, а мягко падает в linear.
  • Mode парсится case-insensitive: ~EASE-IN и ~ease-in эквивалентны.

CHUNK[share-pooled] держит pooled/global conditioning от общего prefix + suffix anchor и по-прежнему раскладывает branch-тексты в cross-attention. CHUNK[share-cross] делает симметричную, но более нишевую вещь: держит общий cross-канал и позволяет branch-веткам влиять на pooled/global часть.
POOL{...} — это не новый backend-комбайнер, а top-level adjunct. Он отдельно кодируется в pooled/global канал, а token-wise cross-attention остаётся от base prompt-а или уже собранного backend-результата. На tensor-only/non-dict пути POOL мягко деградирует в no-op и не ломает старые модели.
ASSEMBLE{enc1=...; enc2=...; pooled=...} — это не честный pre-encode ENCODE. Блок работает post-encode: отдельно прогоняет секции через обычный get_learned_conditioning(...) и затем собирает SDXL-style каналы уже из готовых conditioning-значений. Поэтому он реалистичен для A1111-like runtime, но честно требует SDXL-style dict conditioning.
BLEND^1.0 эквивалентен старому поведению. Значения выше 1 усиливают доминирующие ветки, а значения ниже 1 делают смешивание мягче. Для mean интенсивность меняет нормализованные пропорции, а для sum сохраняет общий raw weight total, но перераспределяет вклад веток. Channel-targeting через @cross и @pooled даёт SDXL-aware режим: можно смешивать только token-wise context или только pooled/global conditioning, не открывая nested backend-мешанину. Каналы @enc1 и @enc2 ещё точнее: они меняют только одну SDXL-style половину 2048-мерного cross-attention контекста и держат вторую половину якорной.
MORPH^1.0 эквивалентен старому поведению. Значения выше 1 усиливают и ускоряют переход между точками, а значения ниже 1 делают его мягче. Optional point weights вроде human*0.8 и cyborg*1.3@0.6 отдельно смещают вклад control-points внутри самого морфа. Channel-targeting через @cross и @pooled даёт SDXL-aware режим: можно морфить только token-wise context или только pooled/global conditioning, не открывая raw embedding surgery. Каналы @enc1 и @enc2 дополнительно позволяют морфить только одну SDXL-style половину cross-attention и держать вторую половину якорной.
Safe sugar не означает свободное смешивание backend-блоков. Поддерживаются только две shorthand-формы: prefix CHUNK{...} middle MORPH{...} и prefix MORPH{...} middle CHUNK{...}. Они разворачиваются через CHUNK-distribution в уже поддержанный conditioning-path. Формы с BLEND, двумя CHUNK, двумя MORPH или произвольным same-branch mixing по-прежнему считаются unsupported.

15) Гайд по Lark-грамматике и backend-интеграции

15.1 Как Lark работает в парсере

Парсер использует гибридный подход: Lark-грамматика (~L5988) отвечает за структурный разбор (AND-композиция, backend-блоки, вложенность, scheduling-конструкции [a:b:N]), а regex-фаза (~L6042) обрабатывает attention-веса, interpolation (word:1.0->2.0) и escaping.

  • Lark запускается только если есть синтаксис, требующий структурного разбора (AND, backend-блоки, scheduling).
  • Plain-промпты без специального синтаксиса идут через regex fast-path (Lark не вызывается).
  • Грамматика определена как lark.Lark(grammar, parser="lalr", ...) — LALR(1) парсер.

15.3 Backend-интеграция (conditioning pipeline)

После Lark-парсинга AST преобразуется в conditioning через цепочку:

  1. Text extraction — _extract_backend_prompt_state выделяет backend-спецификации (CHUNK/BLEND/MORPH/POOL/BIND/ASSEMBLE/COMPOUND) из защищённого окружения
  2. BIND2 transpile — _transpile_bind2_to_chunk преобразует BIND2 в CHUNK до Lark (если transpile-путь активен)
  3. Scheduling extraction — get_schedule собирает [[end_step, text], ...] с учётом backend-специфики
  4. Sequential segments — _extract_sequential_backend_segments обрабатывает mixed-backend промпты (Phase 4)
  5. Conditioning building — _build_prompt_conditioning_schedule рекурсивно диспетчеризует в handler каждого backend
  6. Hybrid batch encoding — plain-тексты кодируются batch-вызовом, nested backend-тексты — по одному
Ключевой принцип: каждый backend-блок — это изолированный сабграф в AST. Lark проверяет только структурную корректность (скобки, разделители). Семантическая валидация (веса, token counts, supported nesting) происходит на этапе conditioning pipeline, а не в грамматике.
